# Замеры ресурсов клиента

Скрипт: [`measure.py`](measure.py). Он считает RAM (PSS, общие библиотеки делятся честно) и CPU всего дерева процессов.

```bash
# запустить и замерить Feather
bench/measure.py run --label feather -- target/release/feather-desktop
# замерить уже запущенное приложение
bench/measure.py attach --label discord --name Discord
```

## Этап 0, замер 1 (2026-10-10)

**Машина:** EndeavourOS, ядро 6.18, Wayland, 12 потоков, 31 ГБ RAM, GPU NVIDIA.
**Feather:** Tauri 2 + WebKitGTK 2.52, SolidJS. 10 000 сообщений в канале, новое сообщение каждые 1,5 с.

| | RAM (PSS) | CPU (% одного ядра) | Процессов | Размер |
|---|---|---|---|---|
| Discord 1.0.161 (реальный аккаунт, свои серверы) | **871 МБ** | 13,9 % | 9 | — |
| Telegram Desktop (реальный аккаунт) | **618 МБ** | 35,5 % | 1 | — |
| Feather, без настроек | 278 МБ | 2,3 % | 3 | — |
| **Feather, с настройками WebKit** | **244 МБ** | **1,3 %** | 3 | бинарник 3,3 МБ, `.deb` 1,4 МБ |
| Пустая страница в той же оболочке («пол» WebKitGTK) | 209 МБ | 0,2 % | 3 | — |

Discord и Telegram замерены с реальными аккаунтами пользователя, поэтому сравнение не идеально точное, но порядок величин понятен.

### Что сработало

| Настройка | Эффект |
|---|---|
| `WEBKIT_DISABLE_DMABUF_RENDERER=1` + `WEBKIT_DISABLE_COMPOSITING_MODE=1` | −35 МБ, CPU 2,3 → 1,3 % |
| `CacheModel::DocumentViewer` | эффект в пределах погрешности, но оставлено (кэш страниц чату не нужен) |
| `JSC_useJIT=false` | ещё −20 МБ, но CPU растёт. **Не применяем** |

### Из чего состоят 209 МБ «пола»

- ~102 МБ — реальная память процессов (anon): GTK, WebKit, сетевой процесс WebKit.
- ~106 МБ — код библиотек (libwebkit2gtk, JavaScriptCore, драйвер NVIDIA, LLVM). Эти страницы общие для всех WebKitGTK-приложений, и при нехватке памяти система может их выгрузить.

### Вывод (по Tauri)

- Наш интерфейс с 10 000 сообщений стоит всего **~35 МБ** сверх пола. Виртуализация и SolidJS работают как задумано (≈200 DOM-узлов, JS heap ≈7 МБ).
- Цель «< 100 МБ» на Linux с Tauri **недостижима**: только WebKitGTK занимает ~209 МБ.
- Feather при этом в **3,5 раза легче Discord по памяти и в 10 раз по CPU** на той же машине.
- Решение по UI-технологии нужно принять, см. [docs/09-decisions.md](../docs/09-decisions.md).
- Ещё не замерено: Windows (WebView2), холодный старт, прокрутка на слабом железе.

## Этап 0, замер 2: Slint против Tauri (2026-10-10)

Тот же экран, те же 10 000 сообщений (тот же генератор и seed), живые сообщения раз в 1,5 с.
Прототип на Slint 1.18 лежит в `client/native`. Режимы бенчмарка: `FEATHER_AUTOSCROLL=1` (Slint) и `index.html#autoscroll` (Tauri) включают непрерывную прокрутку 60 раз в секунду.

| | RAM в покое | CPU в покое | RAM при прокрутке | CPU при прокрутке | Процессов | Бинарник |
|---|---|---|---|---|---|---|
| Discord | 871 МБ | 13,9 % | — | — | 9 | — |
| Tauri (WebKitGTK, с настройками) | 244 МБ | 1,3 % | 286 МБ | 49 % | 3 | 3,3 МБ |
| **Slint, отрисовка через GPU (femtovg)** | **75,5 МБ** | **0,35 %** | 75,5 МБ | 22 % | 1 | 12,7 МБ |
| **Slint, программная отрисовка** | **20,7 МБ** | **0,35 %** | 20,5 МБ | 23 % | 1 | 12,7 МБ |

Окно 1280×800. Разница между режимами (~55 МБ) — это OpenGL-контекст и библиотеки видеодрайвера (здесь NVIDIA).

### Вывод

- Slint легче Tauri по памяти в **3–12 раз**, а при прокрутке тратит **вдвое меньше CPU**. Внешний вид при этом практически такой же.
- Цель «< 100 МБ» выполняется с запасом в обоих режимах отрисовки.
- Ещё не проверено: программная отрисовка на большом экране (2560×1440, полный экран), где нагрузка на CPU при прокрутке может вырасти. Отсюда вопрос, какой рендерер ставить по умолчанию.

## Этап 0, замер 4: голос через LiveKit Rust SDK (2026-10-10)

Прототип: `client/voice-proto`. Звук синтетический (без микрофона и динамиков). LiveKit работает локально в Docker.

```bash
target/release/feather-voice-proto latency        # задержка
target/release/feather-voice-proto peer <имя>     # участник канала для замера CPU/RAM
```

### Задержка

Путь звука: кадр → кодирование Opus → LiveKit → джиттер-буфер → декодирование, всё на одной машине.

| Замеров | Мин | Медиана | Макс |
|---|---|---|---|
| 22 | 38,8 мс | **39,0 мс** | 40,1 мс |

В реальности сюда добавятся сеть (пинг до сервера) и буферы аудиоустройств (обычно 20–40 мс). Цель «< 150 мс рот → ухо» выглядит реалистичной.

### Ресурсы участника (5 человек в канале)

| Сценарий | RAM | CPU |
|---|---|---|
| Один в канале, говорит | 12 МБ | 4,4 % |
| 5 в канале, говорит и слушает 4 человек | 12 МБ | 8,3–8,9 % |
| Сервер LiveKit (5 участников) | 56 МБ | 1,5 % |

**По потокам** (5 в канале):

| Поток | CPU |
|---|---|
| `AudioEncoderQueue` (кодирование Opus) | 4,1 % |
| `SyntheticAudioDevice` (виртуальное аудиоустройство, микширование каждые 10 мс) | 3,6 % |
| сеть и рабочие потоки libwebrtc | 1,8 % |
| наш код (tokio) | 1,5 % |

**Вывод:** память отличная (12 МБ), а CPU в 4 раза выше цели «< 2 %». Почти всё уходит на кодировщик Opus и виртуальное аудиоустройство внутри libwebrtc, а не на наш код. Что пробовать дальше:

1. Перейти на реальные устройства (`livekit::PlatformAudio`): виртуальное устройство заменится настоящим, и тогда замерить заново.
2. Снизить сложность (complexity) кодировщика Opus и проверить, есть ли для этого настройка в SDK.
3. ~~Не кодировать, пока отпущен push-to-talk.~~ **Проверено:**
   - `track.mute()` CPU **не снижает** (8,3 → 11,5 %, в пределах шума): кодировщик продолжает работать;
   - если **не подавать кадры** в источник, кодировщик падает до 0, и итог **8,3 → 5,2 %**. Так и делаем для PTT: при отпущенной кнопке кадры в libwebrtc не отправляются;
   - оставшиеся ~2,6 % — виртуальное аудиоустройство, которое воспроизводит 4 собеседников. Следующий шаг — замер с `PlatformAudio`.
4. Сравнить с Discord в голосовом канале на этой же машине.

## Этап 0, замер 5: настоящий аудиотракт и шумодав (2026-10-10)

Тестовая речь: Open Speech Repository (`bench/audio/fetch.sh`), к ней подмешаны розовый шум, гул 50 Гц и щелчки клавиатуры (`bench/audio/make_noisy.py`, SNR 8,7 дБ). Звук проигрывается в виртуальный микрофон PipeWire (`bench/audio/vdev.sh`). Клиент в режиме `device` берёт его через `livekit::PlatformAudio` (PulseAudio, шумодав/AEC/AGC WebRTC), второй участник (`record`) пишет то, что до него дошло. Анализ: `bench/audio/analyze.py`.

```bash
bench/audio/fetch.sh && bench/audio/make_noisy.py
bench/audio/vdev.sh up
bench/audio/vdev.sh play speech_noisy.wav &
target/release/feather-voice-proto record out.wav 40 &
PULSE_SOURCE=feather_vmic PULSE_SINK=feather_vout target/release/feather-voice-proto device speaker
bench/audio/analyze.py out.wav
bench/audio/vdev.sh down
```

### Шумодав

| | Фон в паузах | Речь | Речь громче фона на |
|---|---|---|---|
| Чистая речь (эталон) | −59,2 дБ | −22,9 дБ | 36,3 дБ |
| Шумный микрофон (вход) | −39,2 дБ | −22,8 дБ | 16,5 дБ |
| **Принято собеседником** (прогон 1) | **−59,2 дБ** | −15,8 дБ | **43,4 дБ** |
| **Принято собеседником** (прогон 2) | **−59,5 дБ** | −14,3 дБ | **45,2 дБ** |

**Вывод:** встроенный шумодав WebRTC убирает фоновый шум примерно на **20 дБ**, до уровня чистой записи. Речь сохраняется, а AGC делает её на 7–8 дБ громче. На слух качество ещё нужно проверить живым голосом.

### Ресурсы с настоящими устройствами

| | RAM | CPU |
|---|---|---|
| Говорящий (PlatformAudio + шумодав/AEC/AGC), 1 слушатель | 16 МБ | 7,7–8,1 % |

### Найденные проблемы

1. **Выбор микрофона на Linux может не сработать.** PipeWire запоминает устройство для приложения `WEBRTC VoiceEngine` (module-stream-restore) и переключает поток туда, даже если в SDK выбран другой микрофон. Обходной путь — `PULSE_SOURCE`/`PULSE_SINK` при запуске или перенос потока через PulseAudio API. В продукте нужно задать своё `application.name` (`Feather`) и проверить, что выбор устройства в настройках действительно работает.
2. **В SDK 0.9.4 программный шумодав/AEC/AGC на десктопе не отключается:** `configure_audio_processing` переключает только аппаратную обработку. Если понадобится режим «чистый звук» (для музыки и стримеров), нужно искать другой способ или патч SDK.
3. CPU голоса по-прежнему около 8 % против цели 2 %. Следующий шаг — профилировать с настоящими устройствами и сравнить с Discord в голосе на этой же машине.

## Этап 0, замер 7: живая запись с улицы и CPU с настоящими устройствами (2026-10-10)

### Шумодав на реальной записи

Пользователь записал на улице речь с уличным шумом (58 с, файл в репозиторий не попадает). Звук прогнан через тот же тракт, что в замере 5: виртуальный микрофон → `device` → LiveKit → `record`.

| | CPU |
|---|---|
| PTT нажат (говорит) | 10,0 % |
| PTT отпущен, `PlatformAudio::stop_recording()` | 10,5–10,7 % |
| Discord в голосе, микрофон выключен (замер 6) | 21,8 % |

Цель «< 2 %» переносится в этап 2 как отдельная задача: собрать свой libwebrtc (Opus complexity 5, кадр 20 мс, остановка кодировщика без сигнала) и замерить. Уже сейчас голос Feather **примерно вдвое легче голоса Discord**.

## Этап 0, замер 8: демонстрация экрана, аппаратное кодирование (2026-10-10)

Ноутбук: Intel iGPU (VA-API, QuickSync) + NVIDIA RTX 3050 Ti Laptop (NVENC, драйвер 615.71). SDK собран с NVENC и VA-API (`CUDA_HOME=/opt/cuda` в `.cargo/config.toml`, libva найден). Захват экрана заменён синтетическими кадрами (12 разных кадров по кругу), потому что на Wayland захват требует выбора экрана в диалоге. Битрейт ограничен 6 Мбит/с, simulcast выключен, зритель — отдельный процесс (`viewer`).

```bash
target/release/feather-voice-proto viewer &
LIVEKIT_PREFERRED_HW_ENCODER=nvenc target/release/feather-voice-proto video 1920 1080 60 h264
```

| | CPU транслирующего | Зритель получает | RAM* |
|---|---|---|---|
| 1080p60, **NVENC** (H.264) | **12 %** | **60 fps** | 161 МБ |
| 1080p60, автовыбор (выбрал NVENC) | 10 % | 60 fps | — |
| 1080p60, VA-API (Intel, H.264) | 13 % | 31 fps | 164 МБ |
| 1080p60, программный VP8 | **80 %** | **8,8 fps** | 219 МБ |
| 1440p60, NVENC | 11 % | 47 fps | 193 МБ |
| 1440p60, VA-API | 18 % | 41 fps | 194 МБ |

\* RAM включает 12 заранее сгенерированных кадров (≈37 МБ для 1080p, ≈66 МБ для 1440p), в реальном клиенте их нет.

**Выводы:**
- Аппаратное кодирование обязательно: программное на 1080p60 съедает ядро целиком и всё равно даёт 9 fps.
- SDK сам выбирает NVENC, если он есть. Нужно проверить приоритет на машинах только с Intel/AMD.
- 1440p не дотягивает до 60 fps на 6 Мбит/с с нашим «тяжёлым» синтетическим контентом (WebRTC сбрасывает кадры, чтобы уложиться в битрейт). Реальный экран сжимается лучше. Перепроверить на настоящем захвате.
- VA-API на Intel выдаёт около 31 fps на 1080p60. Причину (настройки rate control или ограничение iGPU) нужно выяснить.
- Если аппаратного кодировщика нет, демонстрацию нужно ограничивать до 720p30 и предупреждать пользователя.
- В SDK есть путь DMA-BUF (`dmabuf_video_frame_buffer`): захват PipeWire → кодировщик без копирования через CPU. Это следующий шаг, который требует настоящего захвата экрана.

## Этап 0, замер 9: шумодавы на живой записи — оценка на слух (2026-10-10)

**Отзыв пользователя о шумодаве WebRTC (замер 7):** «голос только громче, другой разницы не заметил». Цифры это подтверждают: «разница» 26,6 → 42 дБ получилась в основном за счёт AGC (речь +8 дБ), а фон упал всего на 7 дБ. Классический шумодав WebRTC слаб против нестационарного уличного шума. У Discord для этого нейросетевой Krisp (поток `threaded-ml`, замер 6). **Здесь мы уступаем Discord.**

Сравнение на той же записи (`bench/denoise`, офлайн, тот же файл):

| | Фон | Речь | CPU в реальном времени |
|---|---|---|---|
| Оригинал | −48,9 дБ | −22,3 дБ | — |
| WebRTC NS + AGC (сейчас) | −56,1 дБ | −14,1 дБ | входит в APM |
| **RNNoise** (`nnnoiseless`) | **−65,4 дБ** | −22,5 дБ | **≈1 % одного ядра** |

RNNoise убирает фон на **16,5 дБ** без изменения громкости речи. DeepFilterNet (качественнее, тяжелее) не проверен: репозиторий 175 МБ и не обновлялся с 2024 года. Вернуться к нему как к режиму «максимальное качество».

**Вывод:** нужен свой шумодав перед кодировщиком. В `PlatformAudio` программный NS не отключается и нет точки вставки своей обработки (замер 5), поэтому захват микрофона берём на себя: устройство → RNNoise → `NativeAudioSource` (у него NS/AEC/AGC отключаются через `AudioSourceOptions`). Заодно решается проблема выбора устройства на Linux: своё `application.name` вместо `WEBRTC VoiceEngine`. Решение D17.

## Этап 2, замер 11: голос в клиенте — свой аудиотракт с RNNoise (2026-10-10)

Клиент `feather` в голосовом канале «Лобби»: свой захват/вывод (cpal, PulseAudio), APM WebRTC (эхоподавление, автогромкость, фильтр), RNNoise, `NativeAudioSource`. В канале ещё 2 бота с синтетической речью. Микрофон — виртуальный (`FEATHER_MIC=FeatherVirtualMic`, зашумлённая речь), вывод — виртуальный.

### Качество: что слышит собеседник

**Что нашли:**
- 80 МБ из 199 съедал контекст CUDA: WebRTC проверял видеодекодер NVIDIA при подключении. `LK_DISABLE_NVDEC=1` (клиент ставит сам) убирает это; аппаратное кодирование демонстрации экрана не затрагивается.
- По потокам (слушаю): вывод звука cpal ~3,4 %, служебное аудиоустройство LiveKit ~2,4 %, приём ~1,5 %. Говорю: + кодировщик Opus ~4,5 %, обработка (APM + RNNoise) ~5–7 %. Эхоподавление стоит ~2,7 %.
- RNNoise в реальном времени дороже, чем офлайн (≈4 % против 1 %): короткие всплески работы на низкой частоте процессора.
- **Фиксированный буфер устройства 20 мс в бэкенде PulseAudio ухудшил** нагрузку аудиопотока (3,4 → 8,7 %) — откатили, размер выбирает система.

**Дальше:** настройка «эхоподавление» (в наушниках можно выключить, −2,7 %), RNNoise только на кадрах с сигналом, своя сборка libwebrtc (сложность Opus, без служебного аудиоустройства).
