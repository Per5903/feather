# 02. Производительность клиента

> **Главное требование проекта.** Геймер не должен замечать клиент: ни по FPS, ни по памяти, ни по загрузке процессора.

## Бюджет ресурсов (десктоп)

| Метрика | Discord (ориентир) | Telegram Desktop (ориентир) | **Цель Feather** |
|---|---|---|---|
| RAM, в фоне | 300–700 МБ | 100–200 МБ | **< 100 МБ** |
| RAM, активный чат | 400–900 МБ | 150–300 МБ | **< 150 МБ** |
| CPU в простое | ~0,5–2 % | ~0 % | **~0 %** |
| CPU в голосовом канале | 2–6 % | — | **< 2 %** |
| Размер установщика | ~100 МБ | ~40 МБ | **< 20 МБ** |
| Холодный старт | 3–10 с | ~1 с | **< 1,5 с** |
| Процессы | 5+ | 1 | **1–2** |

Цифры конкурентов примерные и зависят от системы. **Первый реальный замер** (Linux, этап 0): Discord 871 МБ, Telegram 618 МБ, Feather 244 МБ, из них 209 МБ занимает сам WebKitGTK. Подробности и выводы в [bench/README.md](../bench/README.md).

Эталонное слабое железо для тестов: 2–4 ядра, 8 ГБ RAM, встроенная графика, HDD. Клиент обязан укладываться в бюджет и на нём.

## Как укладываемся в бюджет

### 1. Интерфейс: нативный Slint (решение D12)

Первый вариант (Tauri) отклонён по замеру: WebKitGTK занимает ~209 МБ даже на пустой странице. Slint на том же экране занимает 20–75 МБ. Ниже для истории оставлено исходное обоснование Tauri.

#### Было: Tauri вместо Electron

- Electron везёт с каждым приложением целый Chromium и Node.js. Отсюда сотни мегабайт.
- Tauri использует системный WebView (WebView2 на Windows, WebKit на macOS и Linux) и бэкенд на Rust. Установщик весит единицы мегабайт, процесс один.
- **Всё тяжёлое (сеть, кэш, крипто, голос) работает в Rust-ядре, а не в JavaScript.** WebView только рисует интерфейс.

#### Было: SolidJS

- Нет виртуального DOM: обновляется только изменившийся узел, без перерисовки компонентов.
- Небольшой бандл (десятки КБ против сотен у React со всей экосистемой).
- **Виртуализация списков обязательна** для сообщений, участников и каналов. В DOM живут только видимые элементы плюс небольшой запас.
- В памяти UI хранится ограниченное окно истории (например, 200 сообщений на канал). Всё остальное лежит в SQLite-кэше Rust-ядра.

### 3. Правила UI, чтобы «выглядело нормально» и не тормозило

- Анимации только через `transform` и `opacity` (они выполняются на GPU и не вызывают layout).
- **Запрещено:** `backdrop-filter: blur`, большие `box-shadow` на списках, анимированные градиенты, параллакс.
- Анимированные GIF, аватарки и эмодзи **проигрываются только при наведении**. По умолчанию показывается статичный первый кадр.
- Иконки — один SVG-спрайт. Шрифт — системный или один вариативный шрифт с урезанным набором символов.
- Тёмная тема по умолчанию, плоский чёткий дизайн. Хорошо выглядящий интерфейс достигается сеткой, типографикой и цветом, а не эффектами.

### 4. Сеть

- **Ленивая подписка:** полные события клиент получает только по открытому серверу. По остальным приходят счётчики непрочитанного и упоминания.
- **Ленивый список участников:** статусы присылаются только для видимой части списка, как в Discord.
- Бинарный протокол (MessagePack) и сжатие `permessage-deflate`.
- Картинки сервер сам уменьшает до превью в WebP/AVIF нескольких размеров. Оригинал скачивается только по клику.

### 5. Голос и медиа

- Голосовой движок нативный (libwebrtc через LiveKit Rust SDK), а не в WebView. Так меньше нагрузка, а голос работает при свёрнутом окне.
- Opus с DTX: в тишине пакеты почти не отправляются.
- Шумодав RNNoise: лёгкий, уровень нагрузки единицы процентов одного ядра. Тяжёлые ML-шумодавы можно включить только по желанию.
- **Демонстрация экрана через аппаратный кодировщик** (NVENC, QuickSync, AMF), а не на CPU. Это критично, когда человек одновременно играет.

### 6. Игровой режим

Когда на переднем плане полноэкранная игра или окно клиента скрыто:

- рендеринг UI приостанавливается (нет кадров, нет перерисовки);
- события копятся в Rust-ядре, интерфейс обновится при возврате;
- работают только голос, глобальный push-to-talk и уведомления об упоминаниях;
- фоновые задачи (синхронизация, подгрузка превью) откладываются.

Режим включается автоматически, плюс есть ручной переключатель.

### 7. Память

- Все кэши (картинки, сообщения, профили) — LRU с жёстким лимитом.
- Распакованные изображения освобождаются, когда уходят за пределы видимой области.
- Неактивные серверы выгружаются из памяти UI.

## Контроль: бюджет проверяется автоматически

- **Бенчмарк в CI:** запуск клиента, сценарий «открыть сервер → прокрутить 10 000 сообщений → посидеть в голосе 5 минут», замер RAM и CPU. Если бюджет превышен, сборка красная.
- В клиенте есть страница «Диагностика»: текущая память, CPU и сетевой трафик. Пользователь видит, что клиент лёгкий, а мы получаем точные баг-репорты.
- Раз в релиз делается сравнительный замер против Discord и Telegram Desktop на эталонном железе. Результаты публикуются (это хороший маркетинг).

## Главные риски

| Риск | Что делаем |
|---|---|
| WebKitGTK на Linux медленнее и хуже поддерживает WebRTC | Медиа живёт в Rust-ядре, а не в WebView, поэтому WebRTC в WebView не нужен |
| Поведение WebView2 и WebKit отличается | Тестируем UI на всех трёх ОС с первого дня |
| Tauri не уложился в бюджет | **Сработало:** перешли на Slint (D12) |
